# Addendum, 2026-10-03 — one defect fixed, and some artifacts deleted

Two things happened to this directory in the week after the round-2 sweep.
Both are recorded here rather than folded into `REPORT.md`, so the report
stays the document the sweep produced.

## 1. Files were deleted on 2026-09-30, not by this task

Gone from `e2e/`: `findings/` (both write-ups), `_round1/` (the entire round-1
archive — manifest, runs, logs, results, INVENTORY), the round-2 `results/`
and `logs/` directories, and `dryrun/`, `fixtrial/`, `fixtrial_v1_fix1only/`.
The directory mtime is `Sep 30 23:42`. **I do not know what deleted them.**

Survived intact (all `Sep 26` timestamps): `REPORT.md`, `VERDICT.md`,
`INVENTORY.json`, `INVENTORY.csv`, `INVENTORY_RANKED.json`, `manifest.jsonl`,
`_round2_manifest_prefix14.jsonl`, `PROGRESS.md`, `README.md`,
`REPORT_PROSE.md`, every `sweep*.out`, `probes/`, `tools/`, `fixes/`, and —
importantly — **all 161 `runs/<id>/` dump sets**.

`findings/SRC_NEW_DEFECTS.md` and `findings/AUTOLAB_GAPS.md` have been
**regenerated**, with every claim either re-verified against the live tree
today or re-derived from the surviving artifacts, and each one marked as such.

**The round-1 → round-2 comparison cannot be re-run** —

## 2. S-6 was fixed in `src_new` on 2026-09-28, and it is worth 822 atoms

The largest defect this run reported was one line:
`domains/ruby_rails_sql/render.py:classify_note` took the first token of the
RAW note string, and §4.1.1c notes are JSON envelopes, so every structured
note classified `prose` and no atom was renderable. It now reads
`_note_payload(note)`, and its docstring carries the finding back verbatim.

Because the dumps survived, this could be **measured rather than projected**.
`tools/repipe_only.py` re-runs only the Python half over the same 161 dump
sets — no JVM, no re-drive — so the only variable is `src_new`:

| | 2026-09-26 | 2026-10-03 | |
|---|---:|---:|---|
| SQL views rendered, total | 20 | **548** | |
| endpoints rendering ≥1 view | 18 | **123** | of 161 |
| unsupported atoms, total | 940 | **118** | |
| atoms excluded *only* by the envelope misclassification | **822** | **0** | |
| endpoints failing any pipeline stage | 0 | **0** | |

940 − 118 = **822** — exactly what the e2e pipeline's own
`atoms_lost_to_note_envelope` probe predicted on 2026-09-26 by re-asking the
same classifier with the payload unwrapped. The prediction and the recovery
agree to the atom, which is the check that neither was measuring itself. The
note census is unchanged, as it must be: 862 `select`, 88 `write`, 30 `prose`,
0 `absent`.

New results are in `results_s6fix/`. `INVENTORY.json` and `REPORT.md` are
**not** regenerated from them — they remain the record of what the sweep
measured on 2026-09-26, and this table is the delta.

## 3. What this changes in the verdict

`VERDICT.md`'s residue table ranked "822 atoms lost to one line in `src_new`"
as the second-largest item, affecting 122 endpoints, and its first
recommendation was to fix exactly that. **Both are now done.** The remaining
residue is unchanged:

* the gates are still NOT CONFIGURED on all 161 — that is what promoting an
  endpoint from scaffolded to driven means;
* **S-1 is still open and re-verified today** — `string.rb:179` still emits
  `Contains(argument, receiver)`, and `Contains("@", x) ∧ len(x)=5` is still
  `unsat` where the true predicate is `sat`. This is a soundness bug and it is
  now the largest open `src_new` item;
* **S-7 is still open and re-verified today** — `unevaluable_exprs` is still
  absent from `run_complete`'s summary dict (`grep -c` returns 0), so the
  coverage checker's blind spot remains invisible to every automated consumer;
* S-2, S-3, S-5 unchanged; G-1…G-6 unchanged.

Nothing in this addendum rests on a re-drive. The box's long-running
`results3/posts_show` coverage jobs were alive before and after, and nothing
under `src/`, `src_new/`, `results3/` or `results4/` was modified by me — the
three shared target-library files are still byte-identical to the results4
gold, re-checked today.
