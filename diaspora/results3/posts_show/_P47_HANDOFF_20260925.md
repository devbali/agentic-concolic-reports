**INCIDENT, 04:20-04:41 — P47 stole a slot from the protected gate. FIXED.**

`tools/slot` searches slots `1..N` where N is `$CONCOLIC_SLOTS`. **N is a
SEARCH RANGE, not an offset — the tool has no notion of reservation.** P47 set
`CONCOLIC_SLOTS=6` expecting its legs to "land on 4-6" because the
conversations_index gate (which runs `CONCOLIC_SLOTS=3`) held 1-3. Wrong: at
04:20:24 the gate had slot 1 momentarily free between probe batches, a P47 leg
took it, and `tools/slot` holds a lock for the command's WHOLE LIFE — so with
`TIME_BUDGET=36000` that leg would have held a third of the protected job's
capacity for TEN HOURS.

Symptom that led to it: the gate's probe checkpoint went quiet for 8 minutes.
**Do not diagnose starvation from that checkpoint** — it writes once per
4-probe batch, and the gate's workers were at 72-80 % CPU throughout. Per-PID
CPU is the real test; the slot map (`fuser /tmp/concolic-slot-N.lock`) is what
actually names the culprit.

Fix: `_p47_slot.sh`, a PRIVATE lock namespace (`/tmp/p47-concolic-slot-N.lock`,
workers from `$P47_SLOTS`, default 3). Two jobs can only share one namespace if
they AGREE on the pool size; the gate thought 3, P47 thought 6. The remedy is a
separate namespace, not a bigger number — each job then caps itself and the
launcher sizes the total. `_p47_gen_v2.sh` now uses it, with a comment saying
never to go back.

The offending leg (`anon_html`, pid 1912672) was killed — it had produced 0
dumps, so nothing was lost — and relaunched under the private namespace by
`_p47_leg_anon_html_relaunch.sh` (unit `p47-leg-anon-html.scope`, `MemoryMax=4G`).
The other three legs were left running untouched on shared slots 4-6, so the
1100+ dumps they had already produced were preserved.

Correct slot map afterwards:

```
shared slot 1,2,3 -> conversations_index gate (its full pool restored)
shared slot 4,5,6 -> P47 legs auth_html / auth_json / anon_json (pre-fix launch)
p47 slot 1        -> P47 leg anon_html (private namespace)
```

**HOW TO STOP ANYTHING IN THIS DRIVE — explicit PIDs only.** Never
`pkill -f <pattern>`. Every batch in this project shares runner filenames
(`run_dse.rb`, `coverage_report.py`, helper script names), so a pattern match
is NOT scoped to your job and can kill another concurrent agent's processes.
I used `pkill -f "_p47_catch_summaries.sh"` once during this drive; it happened
to match only my own process, which was luck rather than safety, and is
recorded here as a near-miss, not a precedent.

The correct pattern — used for the auth-leg restart — is: resolve the PID,
confirm its parentage or its cmdline first, then `kill` that PID:

```bash
ppid=$(awk '{print $4}' /proc/$P/stat)
case "$(tr '\0' ' ' < /proc/$ppid/cmdline)" in
  *_p47_gen_v2.sh*) kill "$P" ;;          # confirmed mine
  *) echo "NOT MINE -- abort" ;;
esac
```

A leg's scenario is identifiable without guessing, via its stdout fd:
`basename $(readlink /proc/$P/fd/1)` gives `_p47_leg_<scenario>.log`.

Also: do not edit a shell script while a copy of it is running. bash reads
scripts lazily by byte offset, so an in-place edit can make a running instance
execute spliced garbage. Stop it by PID, edit, then restart.

**Do not touch** `fullgate-conversations-index-919r43c.scope` — a different
endpoint's gate, ~41 h in, holding JRuby slots 1-3. P47 was sized around it
(16 cores, load ~15 at launch, slots 4-6 free).

## 3c. B-2 minted its statement in run 1 ONLY — found at 87k, fixed, auth legs restarted

**The defect.** `_p46_patch_b2.py` made `user.person` fire the real association
reader so W3 `find_target` would mint
`SELECT "people".* FROM "people" WHERE "people"."owner_id" = ? LIMIT 1`. Its
docstring correctly rules out a boot-lifetime `||=` memo, because `$posts_user`
is built once (run_dse.rb:137). The memo was avoided; **AR's own
`@association_cache` was not.** `association(:person)` is cached on the record,
and once its target is loaded `.reader` returns it without re-entering
`find_target`. On a boot-scoped user that cache never clears, so the effect is
identical to the memo the docstring rules out.

**Measured on the live corpus at 87 000 dumps:** the note appeared in run **1
only**, of `auth_html` and `auth_json` — 2 dumps in 87 000, 0 in a 6 000-dump
random sample — while 2 859 of 3 000 dumps carried an `assoc_person` var, all
of them the BELONGS_TO direction from other models. W3 fired constantly, just
never for `user.person`.

It "looked green on a spot check" exactly as the recon warned: cand2's 60-dump
differential passed, because `mock_note_check` only needs the note to exist
SOMEWHERE in the corpus and with 25 runs/scenario the first runs are a large
fraction of a small corpus.

**Severity, stated precisely.** `mock_note_check` would still have PASSED on the
full corpus — the 2 run-1 dumps are in it, and the 20k-sample MISMATCH that
surfaced this was an artifact of the sample, not a corpus failure. The real
costs were (a) evidence too thin to survive pruning (the old pipeline pruned
720k -> 206k) or to register in phase-(d) extraction, and (b) 2 anomalous runs
carrying a target-call shape the other 87 000 lack, which perturbs footprints.
Note the footprint effect is CONSERVATIVE — an extra shape can only make
disjointness harder, so it costs licensing rather than being unsound.

**The fix** (`_p46_patch_b2reset.py`): `association(:person).reset` before
`.reader`. Intra-run duplication is already prevented by the W3-memo
(concolic_targets.rb:1200-1211), keyed on `[owner.object_id, reflection.name]`
and cleared on the run label — so one note per run, not one per call.

**Validated** (cand3 vs cand2, 60 dumps each): `auth_html 1/8 -> 8/8`,
`auth_json 0/21 -> 21/21`, anon unchanged at 0/31 (correct — anon runs get
`user = nil`); **path conditions 60/60 identical**; `find_target` call count
2195 -> 2223, i.e. +1 in exactly 28 dumps and no other target's count moved.
Then confirmed on the live relaunched legs: 5/5.

**Surgical restart, not a full one.** The fix cannot touch anonymous runs, so
only the two AUTHENTICATED legs were stopped (by explicit PID, parentage
confirmed first) and relaunched into `p47-auth-relaunch.scope` with the fixed
runner. The 56 376 anon dumps kept accumulating untouched; only the 37 157
pre-fix authenticated dumps were set aside — MOVED, not deleted — into
`v2/_pre_b2reset_auth_20260925/`. Pre-fix leg logs are `*.pre_b2reset`.

**Consequence for timing:** the auth legs now have their own 10 h budget from
10:24, so they finish ~20:24 while the anon legs finish ~14:20. Anything that
watches "the drive" must watch all THREE scopes — that is why
`_p47_catch_summaries.sh` was repointed; watching only the original two would
have stopped it at 14:20 and lost precisely the two summaries whose legs ran
longest.

## 4b. THE FRONTIER IS TRUNCATED — read this before interpreting coverage

At 08:51, 4.5 h in and 71 070 dumps, all four legs report `stack=49996..49999`
— pinned at `STACK_LIMIT` (run_dse.rb:93, default 50 000). At that point
run_dse.rb:502-505 does:

```ruby
if stack.size >= STACK_LIMIT
  dropped += 1
  next            # the child is DISCARDED, not deferred
end
stack.push([my_id, JSON.generate(fl)])
```

Note the ordering: `seen_seeds` dedup happens BEFORE this check, so everything
dropped here is a **novel** seed-set — genuinely lost exploration, not a
duplicate. The design is honest about it (`frontier_entries_dropped`,
`worklist_exhausted`, and `stop_reason` gains "+ STACK_LIMIT truncation"), it
is simply not free.

Order-of-magnitude only, NOT a measurement: auth_html has expanded ~17.6 k
paths at `pcs=35`, so it has generated on the order of 10^5-10^6 novel
candidates against a 50 k frontier. Expect `frontier_entries_dropped` to be
large. **Read the real number from each leg's summary when it finishes** —
that is the number to quote, and it belongs in the corpus's provenance.

WHY THE OLD DRIVE PROBABLY DID NOT HIT THIS: `_gen_base.sh` used
`MAX_RUNS=4000` per round, so each round expanded at most 4 000 paths and the
frontier logged in `_gen_base.log` never grew past ~10 000
(`stack=9921/9961/9975`). Treat that as indicative, not proof — see next.

**THE OLD DRIVE'S FRONTIER ACCOUNTING IS UNRECOVERABLE.** `run_dse.rb:562`
writes `exploration_summary.json` into the runner's directory, so concurrent or
successive legs overwrite each other. An exhaustive scan of EVERY `*.json` in
the batch directory found exactly ONE scenario record carrying
`frontier_entries_dropped` — and it is a 40-run replay
(`runs_executed: 40`, `seed_sets_tried: 0`, mtime 09-24 14:01), not the base
generation. Its `dropped=0` says nothing about the old base drive.

So the claim "frontier truncation is part of why the old corpus left 774/1008
demand sets gapped" is a PLAUSIBLE MECHANISM, not a measured fact, and must not
be quoted as one. v2's numbers WILL be real, because
`_p47_catch_summaries.sh` now captures each leg's summary keyed by the scenario
inside it before the next leg can clobber it.

WHAT THIS MEANS, and what it does NOT mean:
  * It does NOT invalidate the corpus. Every dump in it is a real, distinct,
    correctly-noted run.
  * It DOES mean stage 1 explores a truncated subset of the tree, so
    "the legs drained" must not be read as "the tree is exhausted" unless
    `worklist_exhausted: true` AND `frontier_entries_dropped: 0`.
  * It is very likely part of why the OLD corpus left 774 of 1008 demand sets
    with gaps. Frontier truncation is exactly the mechanism that leaves whole
    subtrees unwalked, and it is what RUNBOOK Phase 2 exists to repair:
    construct runs from Z3 counterexamples rather than hope DFS reaches them.
  * `STACK_LIMIT` is a tunable (`ENV["STACK_LIMIT"]`). Raising it for a future
    drive is worth considering, but it is not a cure — any bounded frontier
    truncates a tree this broad, and memory grows with it (each entry is a
    JSON flip-set string).

Deliberately NOT restarting the drive over this: it would be a fifth restart on
a theory, the truncation is reported rather than silent, and stage 2 is the
designed remedy.

## 5. What to do when stage 1 finishes — in order

0. **Record the frontier accounting.** For each leg, pull
   `frontier_entries_dropped`, `worklist_exhausted`, `stack_remaining` and
   `stop_reason` from its summary and write them into the corpus provenance
   (see §4b). "Drained" is only meaningful alongside these.

1. **Snapshot the corpus.**
   `find $B/v2 -maxdepth 1 -name 'dump_*.json' | sort > $B/_snapshot_v2_$(date +%Y%m%d).txt`
   Use that absolute list as `DUMP_LIST` everywhere from here on.

2. **Stage 2 of the drive (RUNBOOK Phase 2).** Regenerate the
   saturation/context seeds FROM the fresh corpus and run those rounds — stale
   seed files reference dead variable names. Do not reuse the old seed files.

3. **Regenerate `_ctgt_sample/`** — `_p47_mk_ctgt_sample.py`, written for this:

   ```bash
   python3 $B/_p47_mk_ctgt_sample.py --stride 10            # dry run + gate
   python3 $B/_p47_mk_ctgt_sample.py --stride 10 --apply    # install
   ```

   `_concrete_targets.rb` derives the concrete run's traced target list from a
   greedy set-cover SYMLINK directory, not from the batch dir (parsing a
   six-figure corpus would cost ~10 min per scenario). The shipped sample is 4
   symlinks computed 2026-09-10 and pointing into the OLD corpus; it does NOT
   contain `ActiveRecord::Calculations.pluck`, so leaving it in place means the
   concrete run never tags the `mentions INNER JOIN comments` statement and
   mock_note_check stays RED for a reason that is not the corpus.

   The script verifies its cover by re-deriving the target set from the cover
   alone, and carries a **REGRESSION GATE**: any target the old sample minted
   that the new corpus does not is named, and `--apply` REFUSES. That gap means
   one of two things needing opposite responses — exploration has not reached
   that path (drive more) or a phase-(a) fix silently stopped a mock firing (a
   real regression). Decide, then `--allow-lost` if it was the former.

   As of 05:20 on a ~7 500-dump partial corpus the gate reports 3 absent:
   `evilq_like_author`, `evilq_like_public`, `Person.name` — all
   context-specific aliases that fire deep in the tree, consistent with an
   hour-old corpus rather than a regression. **Re-check at drive end**; that is
   also why the sample must be rebuilt AFTER the corpus is final, not during.
   (`Calculations.pluck`, `Relation.any?` and `Base.to_param` are already
   present in v2 and were NOT in the old sample.)

4. **Regenerate `concrete_run.json`** — `bash _concrete_run.sh`. This is
   REQUIRED and it must come AFTER the corpus: `concrete_run_probe.rb:52-63`
   derives its traced targets by globbing dumps. The outside-frame RED clears
   here, not at the targets edit.

5. **Start the withdrawal file EMPTY *and* disable the prior footprints.**
   Both are handled for you by `_p47_covonly.sh`; both are easy to miss.

   The SECOND one is the less obvious: the corpus tripwire
   (`coverage.py:2760-2768`) withdraws any pair this corpus does not confine
   but whose PRIOR footprints were disjoint. `_prior_footprints.json` holds
   footprints measured on the B-4 corpus, where `call_shape` saw CONFLATED,
   VALUE-SENSITIVE shapes — so tripwiring v2 against it produces withdrawals
   that say nothing about v2. The old pass reported `WITHDRAWN_TRIPWIRE=745`.
   The tripwire only ever REDUCES licensing, so this is not unsoundness, just a
   large pessimism derived from a corrupted baseline. Pass
   `NO_PRIOR_FOOTPRINTS=1` and write v2's own with `FOOTPRINTS_OUT`; promote
   that file to `_prior_footprints.json` deliberately, once, when you want a
   later v2 pass tripwired against an earlier v2 one.

   And the first: Move `_confinement_withdrawn.json`
   aside (`.bak_pre_v2_<date>`). A withdrawal records a gate refutation against
   a PARTICULAR corpus; the 564 stale pairs were measured against the B-4
   corpus and would wrongly suppress confinement licences the new one may
   support. The loop is now automatic (fix #2), so it will refill itself.

6. **Coverage-only pass before the full gate** — `_p47_covonly.sh <snapshot> [tag]`.
   The full pass costs about a day; coverage alone answers what stage 2 needs
   (how many demand sets have gaps, and WHICH combinations are missing — the
   input `_p*_construct.py` turns into seed files for `_p44_drive_par.sh`).
   Smoke-tested end to end on v2 dumps.

7. **Run the three cheap checks**, scoped to the new corpus, before
   paying for a gate: `bash _p46_diff.sh checks <dir>` is the pattern, or run
   them directly (a 20 000-dump stratified sample reproduced the full-corpus
   numbers EXACTLY — `note_fidelity RED = 26`, identical note_check targets —
   so iterate on a sample, not on 206 k dumps).

8. **Then the full pass**: `_real8_launch.sh` with `DUMP_LIST` repointed, a
   FRESH `COVERAGE_CHECKPOINT` and fresh `ACHK_*` checkpoint filenames (the old
   ones are keyed to the old corpus — keep them, do not reuse them).
   Budget ~48 G (`MemoryMax=48G`; 32 G was OOM-killed, peak measured 36.9 G).

### The 2 surviving ORDER-DIFF are a characterised instrument artefact

Both are `ActiveRecord::Relation.records` where the real statement carries an
ordering the note does not:

```
real: SELECT "posts".* FROM "posts" WHERE "posts"."guid" = ? ORDER BY "posts"."id" ASC LIMIT ?
note: SELECT "posts".* FROM "posts" WHERE "posts"."guid" = $$(...) LIMIT 1
```

That `ORDER BY` is not in the app's relation — ActiveRecord ADDS it.
`FinderMethods#find_nth_with_limit` (activerecord-5.2.4.3
relation/finder_methods.rb:520-524) calls `ordered_relation`, which at :557-563
is:

```ruby
def ordered_relation
  if order_values.empty? && primary_key
    order(arel_attribute(primary_key).asc)
  else
    self
  end
end
```

i.e. a `.first` on an UNORDERED relation gets `ORDER BY <pk> ASC` injected. The
mock renders the relation at interception time, before `first` applies that, and
it cannot know the caller was `first`. So this is a genuine
`note_fidelity_declared` candidate (verdicts `["ORDER-DIFF"]`) with the citation
above — but ONLY after confirming on the final corpus that it persists, because
a declaration matching nothing is itself reported and counts RED.

Whatever survives gets one of two dispositions:

* **`note_fidelity_declared`** in `completion_config.json` —
  `{"match": "<substring of the REAL sql>", "verdicts": ["LIMIT-DIFF", ...],
  "reason": "..."}`. `MISSING` is **never** declarable, a declaration must name
  both the statement and the verdict, and a declaration that matches nothing is
  itself reported and counts RED — so add these only AFTER measuring that the
  finding persists.
* **A renderer fix**, when the instrument can express the real shape.
  Prefer this: a waiver is for what the instrument CANNOT express.

`mock_note_check` has **no** waiver hook at all (I read all 255 lines; its
"or a waiver" text at :209 is prose that still sets `red = True`), and
DISCIPLINE.md §9 forbids one by name. Its REDs must be minted, not argued.

One known coverage gap, not a renderer bug: `SELECT 1 AS one FROM "posts"
WHERE "posts"."guid" = ?` — the guid-keyed `exists?` path was never explored.
That wants drive coverage.

## 7. src/ findings — LOGGED, NO ACTION TAKEN (by decision)

None blocks completion; all three were measured. `src/` is left untouched to
avoid widening blast radius to the four already-closed endpoints.

* **A. `call_interceptor.rb:119-156` — gap B-1 is too narrow.**
  `update_all(updates)` called as `update_all(unread: false)` puts the hash in
  `kwargs`; the loop only looks up `kwargs[:updates]` (nil), and the B-1
  restoration fires only for a named `*rest`, never a `:req` positional. Result:
  `args = {"updates": null}`, and the note reads
  `UPDATE "notifications" SET (unknown columns) WHERE ...`. **Measured not
  blocking** — both checks pass and `MISSING` reached 0 anyway. Proposed fix if
  it ever matters: extend the existing restoration to the first unfilled
  POSITIONAL slot under the same three additive conditions.
* **B. `empty_relation_emission_audit.py:85-88`** derives the representative
  prefix by string surgery (`X_rows -> X_row_`), so it is blind to mocks whose
  rep is named otherwise — `pluck` (`_plucked`/`_val`) and `ids`
  (`_ids`/`_id`). **Measured zero impact**: 0 note binds and 0 path conditions
  on a rep of an empty `_ids`/`_plucked` list across 6 000 dumps. That is why
  the two structurally-eager sibling mock sites were deliberately NOT patched —
  a PC-changing edit with no evidence of harm and no validating check is not
  justified. Note a fix cannot hardcode `_ids`/`_val` in `src/` (that would be
  diaspora-specific); it needs a config surface or a runtime-recorded rep name.
* **C. `coverage.py:2292`** normalises `withdrawn_pairs` with `tuple(sorted(p))`
  and no arity check, so a malformed entry silently never matches anything.
  Worked around batch-locally: the loader in `coverage_report.py` now skips
  non-pairs loudly.

## 8. Reusable assets built for this

* `_p46_diff.sh` — `build | drive | checks | compare`. The bounded per-fix
  differential harness. `compare` reports PC identity, note deltas and
  error-type deltas. Caveat: its "dump error changed" line compares whole error
  dicts, and tracebacks embed the working directory, so cross-directory runs
  always show a spurious diff there — compare error TYPES.
* `_p46_patch_*.py` — seven idempotent, self-documenting patch scripts
  (`dml`, `pluck`, `limit`, `b5proj`, `b2`, `emptylist`, `aggorder`). Each
  refuses to apply unless its anchor matches exactly once, and each carries its
  own rationale and citations.
* `_p46_corpus20k/` — stratified symlink sample of the OLD corpus that
  reproduces the full-corpus check numbers exactly. Rebuild the equivalent for
  v2; it makes check iteration minutes instead of hours.
* `_p46_emptyseeds.json` — three real seed sets that reproduce the empty-list
  escape, for re-validating fix #9 on any corpus.
* `_p45_b4_ctl/` and `_p45_b4_fix/` — the original B-4 proof.
