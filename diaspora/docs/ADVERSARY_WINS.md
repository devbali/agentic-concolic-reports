# ADVERSARY WINS — ledger

Every win an adversary round scored against a corpus that the engine had
already called `complete: true`, plus the near-misses worth repairing.
Status: **open** (reported, not yet repaired) → **repaired** (batch agent
claims a fix) → **verified** (a later adversary round re-ran the scenario
and it came back clean). A win is only closed by a REAL run, never by a
green script.

Maintained by the coordinator; each adversary round appends its rows
(see `src/end_to_end_completion_checker/concrete/CONCRETE_CHECKER.md`).

## Cross-endpoint patterns (what to check FIRST on every new endpoint)

1. **Link-bearing text.** Any text rendered through `Diaspora::MessageRenderer`
   can contain `diaspora://…/post/<guid>` and issue `Post.exists?`. Pinning
   text to a literal forecloses the family. Hit on 3/3 endpoints.
2. **Every renderable format.** `:mobile` (session switch, `X_MOBILE_DEVICE`,
   explicit format) renders different partials with different reads. Hit on
   2/3 (notifications already modelled html/json/mobile/xml).
3. **A target mock's note must not be a non-SQL string over a body that can
   reach SQL** — nested calls are swallowed silently (N-1).
4. **Collection length must be a decision** (0 / 1 / many). A corpus where
   every list is one row hides empty-state branches, `last`/interior indexes,
   and `count > 0 ∧ rows = []`.
5. **Pinned type/enum columns** (`target_type`, STI `type`) hide whole
   subclass families with their own reads (N-2).
6. **Over-emission counts too**: a note for a statement no real run issues is
   a defect, not a safe over-approximation. Cheap detector: diff the corpus's
   distinct note shapes against the real statements of the concrete runs
   (`tools/note_fidelity_audit.py --runs …`); anything with no real
   counterpart is over-emission.
7. **One fact, one variable.** Two variables for the same fact let the corpus
   reach states the app cannot: a `pluck` with its OWN length seed made
   `messages.size > 0` hold while the pluck was empty, so `last_author`
   issued `SELECT people.* WHERE id = nil` — a read the app cannot make
   (135 of 1 500 dumps, conversations_index 2026-08-28). A derived
   collection's length IS the length of the query that produced it; link
   them rather than seeding both.
8. **A decision over an impossible state inflates the universe.** Verify the
   state is reachable on a REAL record before keeping the decision: a
   `guid == ''` branch was taken in thousands of dumps although
   `after_initialize :set_guid` fills the column on every instantiation,
   loaded rows included (comments_index and conversations_index, both
   2026-08-28). If it is unreachable, pin it WITH a ledger entry after
   checking the pin costs no evidence.

9. **A query parameter fed into a `where` can arrive as an ARRAY.** Modelling
   it as a scalar forecloses the `IN (…)` predicate entirely: conversations_index
   models `params[:conversation_id]` as one `symint` and its corpus contains ZERO
   `IN (…)` notes in 31 846 dumps, while `?conversation_id[]=1&conversation_id[]=2`
   is a plain URL that reaches the action (C-6, 2026-08-29). Check whether each
   param the action reads is a PATH segment (cannot be an array — comments'
   `post_id`) or a QUERY parameter (can be). The same request also settles the
   1-vs-n arity: a one-element array collapses to `= ?`.
10. **A pinned-away FORMAT or PARAM DOMAIN needs its neutrality argument tested,
    not written.** `:js` was excluded on the written ground "a real 500 with no
    data access beyond the html prefix"; measured, it renders the whole html page
    and, with a `conversation_id`, performs the endpoint's WRITE (C-8).
    `params[:page]` was modelled as one boolean; every other value raises
    `WillPaginate::InvalidPage` inside the action and truncates it to the two
    principal reads (C-7). Both are the M-5 pattern: the pin, not the code,
    decides what the corpus can express.

11. **The rig's boundary stubs are model claims.** A stub warden asserts
    "authentication issues one read and nothing else"; a `layout(false)` asserts
    "the chrome reads nothing". Both were false here (C-10/C-11: `UPDATE "users"`
    on the first request of every session; C-12: `tags`, `reports`, tripled badge
    counts on mobile). Replace the stub with the real component before reading
    anything into "no statement outside a frame".
12. **Compare per-shape COUNTS per request, not presence.** `services` ×2 per
    dump (C-13), the visibilities COUNT ×2 (A3-9c), the mobile badge counts ×1
    (C-12) were all invisible to judges that match note families. The concrete
    run gives the per-request count for free; a lint can diff it against the
    corpus ceiling per scenario (`adversary4/_req_stats.py` is the prototype).
